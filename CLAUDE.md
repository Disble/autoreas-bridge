## Project Notes

1. Follow the SDD workflow and active change artifacts under `openspec/changes/`. The entire SDD workflow (explore -> propose -> spec -> design -> tasks -> apply -> verify -> archive) MUST run completely automatically and proactively from start to finish. CRITICAL: THIS OVERRIDES ALL DEFAULT BEHAVIORS AND SKILLS. Never pause for user confirmation or review between phases. Do not ask permission to proceed to the next step. Only stop for hard, unresolvable blockers. If questions arise about preferences or past discussions, search engram memory FIRST rather than asking the user. Execute the rest of the skills exactly as indicated but with ZERO user intervention.
2. **If docs, specs, or archived changes disagree with the codebase, the code wins as the runtime truth. Record the drift explicitly before proposing fixes.**
3. **Final verification MUST be performed by the orchestrating agent itself, not by a subagent.** Subagents may still be used for other phases (proposal, spec, design, tasks, or apply) when appropriate.
4. **After verify passes, the orchestrating agent MUST create the commit before reporting the change as fully verified.** Commit-time hooks and validations are part of the true verification boundary.
5. Load `bridge-testing` for bridge test work.
6. Load `bridge-debugging` for regressions and boundary investigation.
7. Prefer real stored-shape fixture validation with `internal/anime/store/testdata` (synthetic + single-line stored-shape fixtures, cloned from a real database row before `resources/autoreas-data/animes.dat` was deleted in SDD-55) when validating the storage codec's round-trip.
8. Go and frontend files share the same warning-at-400 and hard-fail-above-500 effective-line policy.
9. `go run ./tools/checkgofilesize` is part of the repo-owned pre-commit gate.
10. ESLint `max-lines` in `frontend/eslint.config.js` is the `>500` hard-fail path and must stay. The advisory `frontend-filesize-warning` job left the gate on 2026-08-11; `bun --cwd="frontend" run filesize:warning` is now the only thing that warns at **400**, and it is manual and whole-tree. The 500 ceiling is checked twice: by ESLint `max-lines`, and by `dharness/max-file-lines` through the layer `dharness sync` splices into `frontend/eslint.config.js`. Read `dharness sync`'s "residue" note carefully — it says those plugin rules do not fire under react-doctor's `--staged` pass, which is true and does **not** mean they are off: they run through ESLint. See `docs/file-size-policy.md`.
11. `tools/checkgofilesize/baseline.yaml` is expected to be empty (`files: []`). Temporary oversized Go files are not accepted as permanent state; any exception must shrink and disappear at `<=500` effective lines.
12. For implementation details, see `docs/file-size-policy.md`.

15. Load `app-notification-pipeline` when adding a new toast notification source, modifying the global notification controller, or debugging why a toast does not appear. See `.claude/skills/app-notification-pipeline/SKILL.md`.
16. **The TDD cycle here is RED → GREEN → MUTATE → REFACTOR.** Load `mutation-tdd` after a test goes green. A test that passes with its guard deleted proves nothing, and neither `go test` nor the coverage number will tell you — three such tests have already been caught in this repo. Mandatory for concurrency tests, defensive branches, error/timeout paths, and any test written to close a coverage gap. **On Go, MUTATE means running `ditto staged --exclude-prefix frontend/ --threshold 0.80 --test-command "go test -count=1 -json ./<owning-package>/"`** (add `--dry` to preview the scope) — not hand-picking mutants. It scopes to the lines you staged. **Naming the owning package is not optional:** ditto runs the test command once per mutant, sequentially, so the default `./...` multiplies the whole ~45-package suite by your mutant count. **Keep `-json`:** without it a mutant that never compiled comes back `unknown`, which scores as a KILL, and the mutation score is the one number that does not move either way. Drop `--exclude-prefix tools/` from the example in `docs/mutation-testing.md` when the staged work is itself under `tools/`, or the run measures nothing. Hand-mutation is the fallback for a single guard mid-edit; it mutates where you were already looking, so it confirms a suspicion rather than surveying the change, and on 2026-08-09 four hand-picked mutants all died while the wrapper found a test asserting against the very constant it claimed to pin. Never assert against the production symbol you are pinning — write expected values as literals. When you do hand-mutate, prove the edit applied (`git diff --quiet -- <file> && echo "!! DID NOT APPLY"`): `sd` is NOT installed here, use `perl -0pi -e`. See `docs/postmortems/postmortem-silent-no-ops.md`. **Mutation coverage differs by surface.** The frontend IS automated: `lefthook.yml` runs `test:mutation:staged` with `root: frontend` (Stryker via `frontend/stryker.dlinter.json`), covering only the added lines of staged frontend files. The Go side HAS a runner and it IS the MUTATE step: `ditto staged` with a scoped `--test-command`, over the staged lines. No hook invokes it — ditto recompiles and re-runs the NAMED package's suite once per mutant, sequentially, so cost is (mutants x that suite) on top of an already ~90s gate — so running it is on you, not on the gate. `docs/mutation-testing.md` has the measured table; treat the figures there as scoped-command measurements, not as what a bare `ditto staged` costs. **A multi-minute silent run is the default `./...`, not a broken scope.** ditto prints nothing at all between `Releasing Ditto…` and the final report unless you pass `-verbose`, so a healthy run and a hang are byte-identical — check `--dry` for the scope and the `--test-command` for the cost before concluding anything is wrong. On 2026-08-30 a bare `ditto staged` was killed twice at ten minutes and reported upstream as a tool defect; it was this. The `mutation-tdd` skill is installed globally, not in this repo — load it by name. See `docs/mutation-testing.md`.
17. `docs/learning-log.md` is the "why" vitácora: read it before non-trivial work, and append when you resolve a non-obvious bug or take a deliberate decision. **Append with `node scripts/log-lesson.mjs "the lesson"`, never by editing the file by hand** — the writer stamps the date and enforces the format so it cannot drift. One line, 300 characters maximum; the ceiling is measured against the existing 82 entries (p25 278, median 498, so most of the log had already drifted past its own "one short sentence" rule). A lesson that does not fit has not been extracted yet — put the investigation in an ADR or postmortem and log the one-line lesson pointing at it. This deliberately never blocks a commit: a gate on documentation makes deleting the entry the cheapest way to commit. It complements deterministic guards; it never replaces them.
18. **`git commit` runs the full gate — budget ~90s for a change touching both Go and the frontend, less when it touches only one.** Jobs are globbed to the files they judge, so a docs-only commit runs almost nothing while a Go+frontend commit runs everything. Job output interleaves across the three concurrent groups — read the job name on a failure rather than assuming the last lines belong to the failing job. Give `git commit` a generous command timeout (≥ 5 minutes / 300000 ms) so it is not killed mid-hook. A killed commit leaves the changes staged but unrecorded — just re-run `git commit`; never `--no-verify` to skip the gate. **The gate is bounded on purpose:** every Go job pins `-p=4`/`GOMAXPROCS=4` and vitest pins `maxWorkers: 4`, because Go tools otherwise default to the logical CPU count and a single commit saturated the machine. Nothing enforces those pins — removing them reintroduces the freeze silently. See `docs/pre-commit-performance.md` and `AGENTS.md` → "Pre-commit Gate".

18b. **"The process is alive" is never a smoke test.** A Wails binary logs a complete, healthy Go startup — bindings, event bus, HTTP server — with a totally blank WebView; 1.2.0 shipped exactly that. `frontend-render-smoke` in `lefthook.yml` renders the real production bundle in headless Edge (the same Chromium engine WebView2 runs) and fails if `#root` is empty. Run it by hand with `bun --cwd="frontend" run render:smoke` (~4s). Load `frontend-render-smoke` before claiming a build works, when the built app opens blank, or when adding a route — a new route is NOT covered until it is added to `ROUTE_MARKERS`. Note `src/main.tsx` uses `HashRouter`, so routes are `/#/downloads`, not `/downloads`.

19. Load `bridge-release` for version bumps, installer builds, or shipping a build. The version is declared only in `wails.json` → `info.productVersion`; `build/windows/installer/wails_tools.nsh` is generated by `wails build -nsis` and must never be hand-edited, and `build/bin/**` is gitignored and never committed. **Every release also updates `CHANGELOG.md`** — promote `## [Unreleased]` to `## [X.Y.Z] — YYYY-MM-DD`, leave a fresh empty `[Unreleased]`, and write entries in user language under Keep a Changelog headings (never pasted commit subjects). The version bump, the regenerated installer, and the changelog ship in the same commit. See `.claude/skills/bridge-release/SKILL.md`.

19b. **`dev` is for development; `main` is for deployments only** (adopted 2026-09-01). Land work on `dev` and never commit development directly to `main`. A release exists only after `dev` is merged into `main`, and the tag goes on the `main` commit. This is enforced rather than conventional: the `guard` job in `.github/workflows/release.yml` fails a tag build whose commit is not an ancestor of `main`, before any build minute is spent — but it is the ONLY thing enforcing it, since no branch is protected and `main` is still the default branch. CI is also the default way a build ships: pushing `vX.Y.Z` publishes a GitHub Release with the Windows installer, the Linux tarball and per-platform `SHA256SUMS`. A local `wails build` is a rehearsal for smoke-testing and ships nothing. Corrections are patch releases — never re-cut or move a published tag.

## Frontend Architecture Constraints

1. Files with `.tsx` extensions under `frontend/src/features/` are dumb UI only: HeroUI React + Tailwind, no Wails calls, no `useEffect`, and no business logic.
2. Frontend custom hooks (`use-*.ts`) must follow the strict hook anatomy: imports, signature, refs, state, context/3rd party hooks, queries/mutations, derived state, callbacks, effects, return.
3. Complex frontend modules must use strict colocation with `.tsx`, `use-*.ts`, `*.helpers.ts`, `*.types.ts`, `*.constants.ts`, optional `*.schema.ts`, and colocated `__tests__/`. **No `index.ts` barrel.** Import modules by concrete path (`../CatalogPanel/catalog-panel.helpers`), never through a directory specifier. Measured 2026-08-02: 62% of cross-module imports already bypassed the barrel and 40 of 67 barrels had zero production importers, so the barrel was cost without benefit. See `docs/adr/011-no-barrel-files.md`.
4. `frontend/src/App.tsx` and any future `frontend/src/app/**` files are delivery/composition only. No React state/effect hooks, no direct Wails binding calls, no business logic.
5. Every property in frontend `*Props` interfaces inside `*.types.ts` must be `readonly`.
6. JSDoc is required on **all** frontend code, not only on exported helpers. `dharness/require-jsdoc` and `dharness/require-variable-jsdoc` enforce it through the dharness layer spliced into `frontend/eslint.config.js`, and they also cover private declarations and top-of-file variables, in test files as well as production ones. This rule used to read "every exported helper in `*.helpers.ts`"; that was always narrower than the intent. Adoption is incremental by construction: the gate lints `{staged_files}`, so a file owes its JSDoc the next time it is touched. Measured 2026-08-13: 390 findings across the tree.
7. TDD is mandatory for frontend helpers and hooks: update/create tests first in the colocated `__tests__/` folder.
8. Frontend files over 500 lines must be refactored immediately.
9. Prefer `frontend/src/features/dashboard` as the reference feature structure once introduced.
10. Use `bun --cwd="frontend" run generate:feature <feature> <ComponentName>` instead of manually scaffolding complex frontend feature folders.
11. Load `dnd-kit` for any drag-and-drop work (sortable lists, kanban/multi-column boards): use the new `@dnd-kit/react` + `@dnd-kit/helpers` (React 19 + StrictMode safe, pointer-based for WebView2) — never legacy `@dnd-kit/core` and never native HTML5 DnD.
12. **Long lists load progressively.** Any rail that can render 100+ rows uses an initial batch that grows on scroll-near-bottom — never a full `.map()` of the collection into a scroll container. **Static** lists (count changes only from filter/search/one-shot fetch — Editor, solo download, Catalog) use `useProgressiveListWindow` from `frontend/src/shared/hooks/` and render `items.slice(0, visibleCount)`. **Live** lists (an event stream pushes items into a store — Run history) must NOT use that hook: its render-phase reset snaps the user back to the first batch on every event, so they keep their own reconciliation and reuse only `isNearListBottom` from `shared/helpers/progressive-list.helpers.ts`. There is deliberately no lint rule — "this list can get long" is not statically decidable and an approximate rule would be noise — so the deterministic guard is a DOM-count test per rail (`AnimeEditorWorkspace.windowing.test.tsx` is the reference). Rejected alternatives (ListBox+Virtualizer, fixed-height windowing, backend pagination) are recorded in `docs/adr/012-progressive-list-rendering.md`.
12b. **Stateful shared widgets live in their own `shared/<domain>/` module, not in `features/`.** `frontend/src/shared/ordering/` is the reference: `ordering.types.ts` + `ordering.helpers.ts` hold a generic `OrderingState<TInstance>` drag-and-drop state machine, and `shared/ordering/ui/AnimeScheduleOrdering/` holds the widget built on it. A feature specializes the generic with its own card type (`WorkingState = OrderingState<OrderingInstance>` in Season) instead of re-implementing the transitions. The signal that sent this module out of `features/` was the boundary gate: three features imported it, which is what a misplaced widget looks like. See the comment block in `.dharness/fallow.jsonc`.

13. Reusable dumb components live in `frontend/src/shared/ui/` (`LabeledTextField`, `LabeledSelect`, `LabeledCheckbox`, `PathPickerField`, `AnimeCoverPlaceholder`, …). Compose these instead of hand-writing another `Label`/`Input`/`Select` block; when such a pattern repeats 3+ times, extract a new generic `shared/ui` component (readonly props, JSDoc, colocated test) to cut the JSX duplication and render complexity the Fallow gate flags.
