# Learning Log (Vitácora)

A human-readable record of *why* things in this repo are the way they are:
decisions taken and non-obvious problems solved, so future sessions inherit the
reasoning instead of rediscovering it.

This is a memory aid, **not** a substitute for deterministic guards. Whenever a
lesson can be enforced (linter, test, `go vet`, pre-commit gate), do that too —
this file only explains the *why*, it never replaces the *how*.

## How to append

- One lesson per line, kept to a single short sentence.
- Format: `- [YYYY-MM-DD]: text`
- Newest entries at the bottom. Never rewrite past entries; add a new line if
  something changes.

RENAME TO` carries indexes across under their **old** names, so the five `idx_mobile_request_captures_*` indexes had to be explicitly `DROP INDEX IF EXISTS`-ed for `ensureIndexes` to recreate them as `idx_request_captures_*` — otherwise the database silently kept both the correct and the misnamed index sets. - [2026-07-29]: `mcp-runtime-events-read`'s write path had to solve one hard constraint: `FanoutLogger` freezes its `targets []entrySink` slice at construction, but the persisting sink must be registered before `bridgeDB` exists (logger construction happens before SQLite bootstrap). The fix is a deferred-bind seam — `eventlog.Sink` is constructed and registered as a fanout target immediately (via the new `logger.NewFanoutLoggerWithSinks`, which exports the previously-unexported `entrySink` as `EntrySink` so a `WriteEntry`-only type can be passed), holding an `atomic.Pointer[Queue]` that starts nil. - [2026-07-29]: `get_correlation_timeline`'s capture-side join cannot be `item.RequestID == correlationID`. The capture middleware mints `requestID := uuid.NewString()` local to one handler invocation (`internal/api/capture_middleware.go`); it never enters a context and never reaches domain code, so no runtime event ever carries it as `Fields.CorrelationID` — the real logged values are `anime.patch:<id>:<ts>`, a download `runID`, or a client-supplied `correlationId`. RequestID equality therefore matches approximately never, and because the spec makes an unmatched correlation a *valid empty result* rather than an error, the tool would have returned a permanently half-empty timeline while reporting success. Fixed by matching the `Correlations` envelope's unique identifiers (changelog/activity/conflict ids) as well, and deliberately NOT device names, operation verbs, or outcomes — those repeat across unrelated requests and would return coincidences. Watch for self-fulfilling fixtures: the original test passed only because it set `RequestID: "corr-1"`, proving the code matched itself rather than reality. A true scalar join needs the correlation id propagated into the capture record — a capture-pipeline change, deliberately out of that slice's scope.

- [2026-07-30]: `SQLiteStore.pruneOldestBeyondRetention` counts successful writes in an in-memory field seeded to zero by `NewStore`, so it must prune on the first write of every process and then every `pruneEvery` (200) — without that first-write guard a desktop app with short sessions would never prune at all, and the 20 000-row cap would be enforced eventually rather than continuously. The cap itself was reviewed and kept: the only per-operation emitter (`InstrumentedBus.Publish`) is `debug` and filtered by default, and `idx_runtime_events_time` carries the exact `occurred_at_ms DESC, id DESC` keys the prune's `LIMIT -1 OFFSET ?` walks, so it is an index scan rather than a table sort. - [2026-07-30]: `go test -race` cannot run in this repo — the race detector needs a C toolchain on Windows, which is exactly what `modernc.org/sqlite` (pure Go) exists to avoid.
