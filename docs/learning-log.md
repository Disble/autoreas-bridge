# Learning Log (Vitácora)

A human-readable record of *why* things in this repo are the way they are:
decisions taken and non-obvious problems solved, so future sessions inherit the
reasoning instead of rediscovering it.

This is a memory aid, **not** a substitute for deterministic guards. Whenever a
lesson can be enforced (linter, test, `go vet`, pre-commit gate), do that too —
this file only explains the *why*, it never replaces the *how*.

## How to append

- One lesson per line, kept to a single short sentence.
- Format: `- [YYYY-MM-DD]: text`
- Newest entries at the bottom. Never rewrite past entries; add a new line if
  something changes.

- [2026-07-24]: `capture-middleware-realtime` replaced ~15 scattered per-handler/per-WS-message capture-record call sites with a single transport-level seam per protocol: an HTTP `CaptureMiddleware` wrapping `/api/*` (writing a pending arrival row before the handler runs, then upserting the terminal row from a `capturingResponseWriter`, panic-safe via `defer`), a `captureWebSocketMessage` decorator around the WS reconcile pump, and a hub sink (`MemoryHubConfig.Capture`) for connect/disconnect/broadcast. - [2026-07-25]: `capture-nomenclature-rename` renamed the `mobilecapture`/`mobile_request_*`/`*_mobile_request*` surface to `requestcapture`/`request_*` (packages, MCP tool names, binary, SQLite tables). Two non-obvious findings drove the design: (1) `persistence.EnsureTableSchema` never calls a table's `Migrate` hook for a table it just created — `tableColumns(db, name)` is empty so it takes the `CreateDDL` branch — so a `Migrate` hook on the renamed `requestCapturesTable()` would have silently created an *empty* `request_captures` while every existing row stayed stranded in `mobile_request_captures`; the rename must run as a dedicated bootstrap pre-step (`ensureRequestCaptureTableRename`, `internal/sync/capture_table_rename.go`) *before* the `EnsureTableSchema` loop, proven by `TestCaptureTableRenamePreservesExistingRows` and the orphan regression `TestCaptureTableRenameNeverOrphansDataBehindAnEmptyTable`. (2) SQLite's `ALTER TABLE ... RENAME TO` carries indexes across under their **old** names, so the five `idx_mobile_request_captures_*` indexes had to be explicitly `DROP INDEX IF EXISTS`-ed for `ensureIndexes` to recreate them as `idx_request_captures_*` — otherwise the database silently kept both the correct and the misnamed index sets. The MCP tool rename (`search_mobile_requests` → `search_requests`, etc.) shipped with **no aliases**: old names are rejected as `unsupported`, forcing a rebuilt `autoreas-request-mcp` binary and a `.mcp.json` update in the same change, because aliasing would have kept the wrong nomenclature alive indefinitely on a surface the sidecar spec deliberately bounds to four tools.

- [2026-07-29]: `mcp-runtime-events-read`'s write path had to solve one hard constraint: `FanoutLogger` freezes its `targets []entrySink` slice at construction, but the persisting sink must be registered before `bridgeDB` exists (logger construction happens before SQLite bootstrap). The fix is a deferred-bind seam — `eventlog.Sink` is constructed and registered as a fanout target immediately (via the new `logger.NewFanoutLoggerWithSinks`, which exports the previously-unexported `entrySink` as `EntrySink` so a `WriteEntry`-only type can be passed), holding an `atomic.Pointer[Queue]` that starts nil. - [2026-07-29]: `get_correlation_timeline`'s capture-side join cannot be `item.RequestID == correlationID`. The capture middleware mints `requestID := uuid.NewString()` local to one handler invocation (`internal/api/capture_middleware.go`); it never enters a context and never reaches domain code, so no runtime event ever carries it as `Fields.CorrelationID` — the real logged values are `anime.patch:<id>:<ts>`, a download `runID`, or a client-supplied `correlationId`. RequestID equality therefore matches approximately never, and because the spec makes an unmatched correlation a *valid empty result* rather than an error, the tool would have returned a permanently half-empty timeline while reporting success. Fixed by matching the `Correlations` envelope's unique identifiers (changelog/activity/conflict ids) as well, and deliberately NOT device names, operation verbs, or outcomes — those repeat across unrelated requests and would return coincidences. Watch for self-fulfilling fixtures: the original test passed only because it set `RequestID: "corr-1"`, proving the code matched itself rather than reality. A true scalar join needs the correlation id propagated into the capture record — a capture-pipeline change, deliberately out of that slice's scope.

- [2026-07-30]: `SQLiteStore.pruneOldestBeyondRetention` counts successful writes in an in-memory field seeded to zero by `NewStore`, so a process persisting fewer than `pruneEvery` (200) events never prunes — the common case for a desktop app with short sessions, meaning the 20 000-row cap is enforced eventually rather than continuously. The cap itself was reviewed and kept: the only per-operation emitter (`InstrumentedBus.Publish`) is `debug` and filtered by default, and `idx_runtime_events_time` carries the exact `occurred_at_ms DESC, id DESC` keys the prune's `LIMIT -1 OFFSET ?` walks, so it is an index scan rather than a table sort. No age-based retention axis was added — bounding a resource twice to solve an unobserved problem is complexity, not safety.
- [2026-07-30]: `go test -race` cannot run in this repo — the race detector needs a C toolchain on Windows, which is exactly what `modernc.org/sqlite` (pure Go) exists to avoid. The product stays cgo-free; `-race` is a dev-tool gap, not a shippable dependency. Concurrency tests therefore assert *logical* invariants (work not lost, duplicated, or stranded) via the new `internal/testsupport/async` package: `Eventually` sleeps between checks because it waits on real work, while `AwaitState` yields with `runtime.Gosched` because it waits to observe a precise interleaving that a sleep would step over. Be honest about the limit: neither helper can detect a data race, only its consequences. Extracted after the pattern appeared twice (`requestcapture.Queue` stop-guard, `eventlog.Sink` pre-bind buffer); 16 call sites across 11 files now share it, replacing hand-rolled deadline loops whose timeouts had drifted to 300ms/500ms/2s for no reason. The channel-`select`+`time.After` helpers in `internal/download` are deliberately NOT migrated — blocking on a channel beats polling, and they were only caught by a name-based grep, not by shape.
- [2026-07-30]: Mutation-check every test that claims to cover a concurrency guard: delete the guard, confirm the test fails. The first version of `TestSinkConcurrentWriteDuringBindDeliversExactlyOnce` PASSED with `writeUnbound`'s under-lock queue re-check removed — 100 goroutine iterations never produced the interleaving (load nil -> deschedule -> `Bind` completes), so the test proved nothing while looking rigorous. The fix was `TestSinkWriteUnboundEnqueuesWhenBindRacedIn`, which calls `writeUnbound` directly on an already-bound sink to reproduce that state deterministically, and does kill the mutant. Defensive branches the scheduler cannot reach need direct invocation, not stress loops.
- [2026-07-30]: Gremlins mutation testing MUST be run from a node_modules-free checkout (a git worktree), never the repo root: gremlins copies the whole module tree into a temp workdir per worker, so `frontend/node_modules` (~130k files) turns a 16-second run into a 12-minute one that never reports. `exclude-files` does not help — it filters mutant selection, not the copy.
