What the Activity screen shows for each kind agreed with mobile. Sample day: the owner's tablet, Sat, Nov 7, 09:00 – 12:00, 33 to 39 check-ins an hour; the death, silence and close are a staged story around it. "Now" is 13:10. Everything outlined in a dashed pink line is new; everything else is copied from the real UI on feat/failed-sync-readings.

Copied from the real UI

  • Page header, phone status line ("Phone connected · last sync 6 min ago"), 24 h chart, range field, origin switch, type toggles with gray count and red failed chip, failure pill.
  • Feed row: time, origin tile (red failed, gray neutral), subject, detail, ×N badge, Copy for AI on failed rows, chevron.
  • Traffic hour row "Phone checked in" + ×N; its drawer: check-ins / refused / slowest tiles and Hour.
  • Drawer header with Technical details, Copy for AI, Close; facts, cause box ("Recorded message" + code chip), timeline dots, "These details are kept until …".
  • Technical view tabs Requests · Events · Data; the "No presenter for api.listening" note; the "Bridge started" generic layout.
  • Default filters: Traffic and System start off.

New in this proposal

  • P1 hourly_summary: no feed line; the Traffic hour row gains an amber "tablet N" chip only when the tablet counted more; the drawer gains "The tablet's count".
  • P2 runtime_transition: "Sync service · died" failed line, other changes neutral; owned by Traffic.
  • P3 native cycle_report: "Sync cycle · failed while sending", and a stage timeline in the drawer.
  • P4 Silence alarm: "Tablet silent" failed line and incident; on return it reads how long.
  • P5 Bridge closed: "Bridge closed" System line; "Bridge started" says how long Bridge was off, or that it did not close normally.

Not proposed

  • MCP status and per-kind coverage changes: they have no screen.
  • Host or remote address capture on reports: undecided by the owner, so no field shows it.
  • Non-failed cycle_report lines: still decided against (they flood the feed).
  • "Bridge off" bands in the feed or chart: the chart's hatched slot stays "No activity".
  • Notifications or toasts for the silence alarm.

P2 · runtime_transition lines Proposal · $$$$

Owner: Traffic. The design places every mobile report under Traffic ("Failed reports only, under Traffic"), and System is the section for Bridge's own starts, warnings and errors that no other type owns. A transition is a report the phone sends about itself, so Traffic owns it. Its failure still surfaces while Traffic is off, through Traffic's red chip. A death of the sync process is a failed line with an incident; every other change (sync started, main started) is a neutral line, which the failure switch skips. The row time is when it happened on the tablet; the drawer shows the late arrival with the existing amber chip.

P4 · Silence alarm Proposal · $$$$

Bridge raises it when it has been on and has heard nothing from the tablet for 60 minutes. Owner: Traffic, origin Bridge: it is about the phone's check-ins, but Bridge noticed it. It is a failed line with an incident, so it counts in Traffic's red chip. The clock counts only time Bridge was on: it starts at the later of the tablet's last contact and the Bridge start. Example: Bridge closed at 23:46, the tablet was last heard at 23:40, Bridge started at 08:58 and heard the tablet at 09:00. The clock started at 08:58, so no alarm. While silent the row reads "since 11:56"; when the tablet returns it reads how long.

P5 · Bridge closed Proposal · $$$$

A clean shutdown writes one event. It shows as a System line "Bridge closed", grouped per hour like every System line. The next "Bridge started" line pairs with it: its detail reads "off 9 h 12 min". A start with no clean close before it reads "did not close normally" in plain muted text, not red: a power cut or a kill is not a failure Bridge can prove, and red is spent only on failures. The chart keeps its "No activity" hatch; it still draws no "Bridge off" band.
