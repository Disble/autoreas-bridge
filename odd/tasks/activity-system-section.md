# Activity System section

Objective: replace the always-shown "bridge" catch-all with a "System" section that owns every feed line no other section claims, grouped like the other sections. Branch `feat/activity-system` (worktree `autoreas-bridge-worktrees/activity-system`, based on `feat/activity-redesign` f51e9420), merged back locally into `feat/activity-redesign`. Delivery: ask-on-risk. Runners: `go test`, Bun/Vitest.

## Specs

- S1 System is the default section. User: "necesitamos un default fallback para todos estos casos que no encajar estrictamente en alguna sección ... (claro, que esto nos podría llevar a falsos positivos, pero es mejor que no tener control sobre estos)". Name: "System" ("me gusta más System que Bridge, tiene más sentido como nombre de sección"); "Bridge" stays the origin filter value only. The wire FeedType `bridge` becomes `system`.
- S2 System is a toggleable section like the others: no line bypasses the type filters any more (removes "bridge lines always shown", `feed.go:83`). Bridge started/stopped belong to System.
- S3 Ownership, not a domain exclusion list: a runtime event belongs to Task when its domain is `schedule` or `season`; to Downloads (not shown as its own line) when its `correlation_id` is a `download_runs.run_id`, because the run line already restates it; otherwise to System. Same noise rules as today (`noiseFilter`, `restatingEventFilter`); only `api.listening` and warn/error events make System lines (info events stay out).
- S4 Grouping, to match the other sections (user: "el problema que resolvía agrupando datos para evitar logs redundantes que comen memoria ... revises lo que realmente necesita una nueva sección "system" para que sea acorde al resto de secciones"): one System line per (hour, domain, event_type, level, message), showing its count ("N times") and first/last time, paged with an hour cursor like traffic. "Bridge started" is grouped per hour too (user: "Agrúpalo por hora, como recomiendas."). Measured on the live DB: 112 lines → 57.
- S5 A System group fails when any member is an error; otherwise it is slow when any member is a warning. Its incident link is the newest incident in that hour with fingerprint `error_event|domain|event_type`. Lines are never built from incidents (they are trimmed to 3 first + 3 latest per fingerprint).
- S6 Counts agree with lines: the per-type counts and overview chart slots count System groups with the same key as the lines, so chips, chart and list match. Invariant test: per-section counts equal the lines the feed returns for the same filter.
- S7 Storage, write paths and retention are unchanged; only the read changes.
- S8 Frontend: a "System" type chip (icon, label), the drawer presenter for System lines (today keyed on `'bridge'`), the failure-menu row, tests and the layout fixture. User decisions on what shows: "Sí se muestran, con los filtros correctos no debería haber problemas."
- S9 Docs: `docs/ubiquitous-language.md` gains an Activity entry (Bridge origin vs System section; line vs event: a line may group N events); the redesign design doc v2 is updated for System; a short ADR records "total classification with a System fallback, grouped on read".

Out of scope here: the nested filter hierarchy (failures within selected sections, proportional chart red, removing the failure menu); it is a separate task after this one.
