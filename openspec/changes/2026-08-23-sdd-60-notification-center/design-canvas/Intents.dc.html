One operation, many carriers

A notification is not the author of an action. It is the carrier of a token pointing at an operation the app already registered — Android's PendingIntent, applied here.

1 · The app owns the registry

Each bounded context registers its own operations as the app comes up. Notifications do not own this list — they are one consumer of it.

download.run_anime→Service.RunAnime
download.run_once→Service.RunOnce
schedule.run_missed→missed-schedule use case
schedule.ignore_missed→missed-schedule use case
navigation.open→route
download.retry_run→nothing. never registered.

The shape already exists in this repo — SiteRegistry / StaticRegistry in internal/download/registry.go.

2 · The record stores tokens, not buttons — at two levels

// about the whole notification "actions": [{ "label": "Open Downloads", // copy. changeable. "intent": "navigation.open", // a key. resolved on press. "args": { "route": "/downloads" } // bound now. immutable. }], // about one row of the list "items": [{ "entity": { "type": "anime", "id": "a-4417" }, "status": "stopped", "detail": "episode 16 failed on every hoster", "actions": [{ "label": "Run this anime again", "intent": "download.run_anime", "args": { "animeId": "a-4417" } }] }]

Same token shape either way. A row's action is not a special case — it is the same immutable address, bound to that row's entity. Nothing executable is stored at either level, which is why both survive a restart.

None of them knows what the operation does. That ignorance is the feature: it is what stops every new surface from re-deriving the same five buttons.

Resolved on press, not on create

This dissolves the ordering problem outright. It no longer matters that the notifier is built at app_startup_runtime.go:139 while the download service does not exist until app.go:243 — creating a token resolves nothing.

Arguments are frozen at creation

Android calls this FLAG_IMMUTABLE. Whoever holds the token may fire it; nobody may rewrite it. An unregistered intent is refused, so a stored string can never reach a shell, a URL, or a method by name.

The duplicate route disappears

RunMissedScheduleNow and IgnoreMissedSchedule stop being a rival path and become another carrier of the same registered intent. One operation, many holders — nothing to pick a winner between.

The one thing the pattern will not do for you: you cannot hold a token to something that does not exist. grep -rn "Retry" internal/download/ returns zero non-test hits — the service is RunOnce and RunAnime, nothing else. A registry makes that impossible to fake, which is the point.
