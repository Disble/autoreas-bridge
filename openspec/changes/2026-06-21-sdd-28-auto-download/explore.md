# Exploration: Automated Anime Downloading — from PoC to Official Feature

## Context & Goal

The PoC at `cmd/poc/*.go` (10 files, all `package main`) validated end-to-end: read today's active animes from bridge SQLite (`anime_snapshots`), scrape jkanime.net for new episodes, batch-download via MyJDownloader by hoster priority, detect completion via filesystem polling, flatten JD's package subfolders, and notify. The PoC mashes scraping, hoster ordering, JD integration, filesystem accounting, decision logic, and notification into a single `package main`. Goal of this exploration: catalog every responsibility, map it onto `autoreas-bridge`'s hexagonal architecture (bounded contexts + event bus + SQLite + Wails), apply concrete patterns borrowed from `dlexa` (a sibling Go scraping project), and surface the data/UI/risk decisions the proposal/design phases must resolve.

## DLEXA Architecture Findings

Read `D:\dev\eln\stylistic\dlexa\internal\{app,source,fetch,parse,normalize,render,query,cache,modules,config,doctor}` and `cmd\dlexa\main.go`.

dlexa's pipeline is: **`source` (registry of named providers) → `fetch` (HTTP retrieval with governance) → `parse` (per-source HTML/JSON parsers via `engine.Resolver`) → `normalize` (schema unification) → `query.LookupService` (fan-out + cache + merge) → `render` (format-specific output) → `modules` (CLI command composition) → `app.App` (composition root)**.

Concrete patterns worth adopting:

1. **`source.Source` interface + `source.StaticRegistry`** (`internal/source/interfaces.go`, `registry.go`): every external provider implements `Descriptor() model.SourceDescriptor` (name + priority) and `Lookup(ctx, request)`. The registry sorts by `Priority` once at construction and resolves a request to a filtered, ordered subset (`SourcesFor`). **Adopt**: this is precisely the right shape for "per-site scraper" (jkanime today, others later) AND for "hoster priority ordering" — both are priority-ordered named providers resolved through a registry, not hardcoded `if`/`switch` chains like the PoC's `strings.Contains(pagina, "jkanime.net")` and the PoC's static `hosterPriority` map.

2. **`engine.Resolver`** (`internal/parse/engine/resolver.go`): a typed map-based registry (`RegisterArticle`/`ResolveArticle`, `RegisterSearch`/`ResolveSearch`) keyed by source name, returning a typed parser interface, erroring loudly when a source has no registered parser. **Adopt**: directly maps to "site adapter registry" — `RegisterEpisodeScraper("jkanime", ...)`, future `RegisterEpisodeScraper("animeflv", ...)`. Avoids the PoC's single hardcoded `jkanimeScraper` struct with site-specific method names.

3. **`fetch.GovernedDoer`** (`internal/fetch/governed_doer.go`): wraps an `http.Client`-like `Doer` with bounded exponential-backoff cooldown specifically for HTTP 429, respecting `Retry-After`, capped at `CooldownMax`, thread-safe via mutex. **Adopt**: jkanime/hoster pages are exactly the kind of upstream that will start 429-ing or showing captchas under repeated polling; a governed transport wrapper is a clean place to enforce backoff without polluting scraper logic, and is independently testable.

4. **`cache.Store` interface** (`internal/cache/interfaces.go`) with explicit contract: cache errors are non-fatal, `Set` is best-effort, never block on cache failure. **Adopt the contract style** (not necessarily the cache itself) — any persistence read in the new download context (e.g. hoster-order config, JD device cache) should follow the same "degrade gracefully, never block the user path" discipline already established for `cache.Get`.

5. **`doctor.Runner`** (`internal/doctor/interfaces.go` + `noop.go`): a single `Run(ctx) (Report, error)` health-check contract returning named `Check{Name, Status, Detail}` entries, aggregated into `Report{Healthy, Checks}`. **Adopt**: "is JDownloader online", "is jkanime reachable", "is the destination folder writable" are exactly doctor-style checks. A `download.HealthChecker` (or reuse of a shared `doctor` package promoted to top-level `internal/`) gives the future management UI a structured place to show "JD: online", "jkanime: reachable", "schedule: next run in 4h" without inventing ad hoc booleans.

6. **`query.LookupService`** (`internal/query/service.go`): orchestrates parallel fan-out across N sources via goroutines + `sync.WaitGroup`, collects `sourceOutcome{source, result, err}`, sorts by priority, merges into one `LookupResult`, with per-source errors becoming non-fatal `Problem` entries appended to the result rather than aborting the whole operation. **Adopt this exact failure-isolation pattern** for "scrape all of today's active animes" — the PoC's `runPoCFull` loop already does this informally (per-anime `fmt.Printf` + `continue` on error) but it is not structured, not testable in isolation, and not observable through the bridge's `logger.Logger`/event bus.

7. **`app.App` composition root** (`internal/app/app.go`): a single struct wiring `platform`, `config`, `doctor`, `registry`, `envelope` (renderer), with `ExecuteModule` as the one orchestration entrypoint that loads config, resolves defaults, validates format, dispatches to a `modules.Module`, and renders success/fallback uniformly. **Reject reproducing dlexa's CLI-specific `modules.Module`/`render.EnvelopeRenderer` abstractions wholesale** — autoreas-bridge already has its own composition root (`app.go` `NewApp`/`startup`) and its own Wails-binding-facing surface; we should mirror the *spirit* (one orchestrating service per bounded context, wired in `app.go` exactly like `device.Service`/`bridgeSync.TriggerService` already are) rather than import dlexa's CLI/rendering machinery, which solves a different UX problem (multi-format terminal output, not a Wails-bound desktop feature).

8. **Config layering** (`internal/config/static.go` + `RuntimeConfig`): defaults are colocated as named constants (`DefaultDPDBaseURL`, `DefaultSearchCooldownBase`, etc.) and assembled into one `RuntimeConfig` struct via `DefaultRuntimeConfig()`, with a `Loader` interface allowing static or dynamic sources later. **Adopt the shape**: a `download.RuntimeConfig` struct with named defaults (hoster priority list, JD poll intervals, schedule cadence) is more testable and discoverable than the PoC's free-floating package-level `var hosterPriority = map[string]int{...}`.

### What to reject from dlexa

- dlexa's `render` package (Markdown/JSON envelope rendering for CLI output) is irrelevant — autoreas-bridge has no CLI surface for this feature; output is Wails bindings + SQLite + event bus.
- dlexa's `modules.Registry`/`Module` CLI-command abstraction is overkill; the bridge already composes bounded-context services directly in `app.go`.
- dlexa is single-process, no concurrent writers, no append-only legacy file, no cross-device sync — none of autoreas-bridge's hardest constraints (Windows file locking, Self-Echo avoidance, append-only `animes.dat`) have a dlexa analog. Do not look to dlexa for guidance on concurrency-with-the-writer; that must come from the existing `internal/anime` design instead.

## Current autoreas-bridge Hexagonal Map

Confirmed by reading `docs/architecture.md`, `internal/anime/`, `internal/sync/`, `internal/device/`, `internal/events/`, `app.go`, `main.go`, `internal/api/router.go`, `internal/logger/logger.go`.

### Bounded contexts today
- **`internal/anime`** — owns `animes.dat` parsing/writing/watching (domain/raw legacy compat in `internal/anime/domain/anime_raw.go`), append-only writer with Self-Echo registry, startup catch-up coordinator, runtime watcher, query/write services (`anime.NewQueryService`, `anime.NewWriteService`).
- **`internal/sync`** — `bridge.db` SQLite bootstrap (`sqlite_bootstrap.go`), changelog recorder/store, conflict store, status service, trigger service, anime snapshot store (the literal source the PoC reads via raw `database/sql` — should instead go through `bridgeSync.NewAnimeSnapshotStore` / `anime.NewQueryService`).
- **`internal/device`** — pairing tokens + device store + auth service; the cleanest small bounded-context template (`Service` port + `SQLiteStore` adapter + `contracts.DeviceInfo` DTO). **This is the best structural template for the new `download`/`acquisition` context.**
- **`internal/api`** — HTTP surface (`/api/*`) for **paired mobile/tablet devices only**, bearer-token authenticated. **Not relevant to this feature** — the download/acquisition feature is desktop-only and should expose itself through Wails bindings in `app.go`, not through `/api/*`. (`internal/api/router.go` confirms every handler requires `h.authenticate`, i.e. a paired device token — wrong shape for a feature with no mobile counterpart.)
- **`internal/events`** — `events.Bus` (`MemoryBus`, pub/sub by event name string), wrapped by `events.NewInstrumentedBus` for logging. Existing events: `anime.changed`, `anime.update_requested`, `anime.write.failed`, `sync.requested`.
- **`internal/logger`** — shared `Logger` interface (`Debugf/Infof/Warnf/Errorf/Logf`) producing canonical `LogEntry{Timestamp, Domain, Level, Message, CorrelationID, EntityID, EventType, DurationMs, Metadata}` (SDD-20 observability-v2 already delivered this rich shape). `FanoutLogger` writes to `StdoutLogger` + `MemLogger` (ring buffer, default capacity 500, emits `observability.log` Wails event on write).
- **Composition root**: `app.go` `App` struct holds every service as a field, wires constructors with override hooks (`new*` function fields default to real constructors, overridable in tests) — exactly the seam a new `download` context must plug into (`a.newDownloadService`, `a.downloadService`, etc., following the existing `a.newDeviceStore`/`a.deviceStore` pattern).
- **`main.go`**: minimal Wails bootstrap — `wails.Run` with `OnStartup: app.startup`, `OnShutdown: app.shutdown`, `HideWindowOnClose: true`, `Bind: []interface{}{app}` (the entire `App` struct's public methods become the JS-callable binding surface).
- **Frontend**: `frontend/src/features/{anime,dashboard,network}/ui/...` with strict colocation (`ui/<Component>/<Component>.tsx` + optional `use-*.ts` + `__tests__/`). `frontend/src/app/routes/*Route.tsx` are the composition/routing layer. `NetworkPanel` (filter bar + table + detail master/detail pattern) is the closest structural precedent for a download-management/log-viewing UI; `dashboard/ObservabilityPanel` is the closest precedent for a live log feed.

### Where the new context fits
A new bounded context — call it `internal/download` (or `internal/acquisition`, naming is a proposal-phase decision) — should:
- Own a `Service` (port) analogous to `device.Service`, orchestrating: trigger decision (online vs disk), site-scraper resolution, hoster-ordered link selection, JD enqueue, completion polling, persistence of last-known counts.
- Depend on `anime.AnimeQueryService` (read-only) to get today's active animes — **not** raw SQL against `anime_snapshots` like the PoC's `bridge.go` does. This reuses the existing `contracts.AnimeQueryService.ListAnimeItems`/`GetEffectiveAnime` surface instead of re-deriving tri-state legacy parsing.
- Publish new events on the existing `events.Bus` (e.g. `download.episode_available`, `download.completed`, `download.failed`) so `sync`/observability/UI can subscribe without new coupling — mirrors how `sync` and `device` already subscribe to `anime.changed`.
- Persist its own tables in `bridge.db` via the same `SQLiteBootstrap` pattern (see Data Management section).
- Expose Wails-bound methods on `App` (e.g. `GetDownloadConfig`, `SetHosterPriority`, `TriggerDownloadCheck`, `GetDownloadLogs`) — same shape as existing `GetSyncingAnimeItems`/`GetPairingToken`.
- NOT touch `internal/api` — no mobile/tablet surface needed unless a future change explicitly requests remote-trigger capability.

## Data Management Analysis

Current pattern (from `internal/sync/sqlite_bootstrap.go`): all DDL lives in one `initializeBridgeDB(db)` function as `CREATE TABLE IF NOT EXISTS` constants, `PRAGMA journal_mode=WAL` + `PRAGMA busy_timeout=5000` enforced and **verified by re-querying the pragma value** (fails loudly if the driver didn't actually apply it), `db.SetMaxOpenConns(1)` (single-writer discipline), schema-evolution handled by explicit column-introspection + migration functions (see `ensureChangelogSchema`/`migrateLegacyChangelogSchema` — rename-old-table → create-new-table → copy-rows → drop-old, all inside one transaction). **New tables for this feature must follow this exact pattern**: add DDL constants, call from `initializeBridgeDB`, and if a future schema change is needed, add an `ensureXSchema` migration function following the changelog precedent — never an ALTER-in-place without a column-introspection guard.

Proposed new tables (concrete, for the design phase to refine):

1. **`download_hoster_priority`** — user-configurable per-site hoster ordering.
   - Columns: `site TEXT NOT NULL` (e.g. `"jkanime"`), `hoster TEXT NOT NULL` (e.g. `"Mediafire"`), `priority INTEGER NOT NULL`, `enabled INTEGER NOT NULL DEFAULT 1`. PK `(site, hoster)`.
   - Seeded with current PoC defaults (`Mediafire=0, Mega=1`) on first run if empty.
   - Read by the `download.Service` once per scrape cycle (or cached with explicit invalidation on UI write) — degrade-gracefully if table is empty (fall back to alphabetical, never crash).

2. **`download_site_config`** — per-site scraper config (currently only jkanime, but must not hardcode for one site).
   - Columns: `site TEXT PRIMARY KEY`, `base_url TEXT`, `enabled INTEGER NOT NULL DEFAULT 1`, `last_success_at_ms INTEGER`, `last_error TEXT`.
   - This is the "multi-site extensibility" anchor the user flagged as omitted — without this table, adding a second site means another hardcoded `strings.Contains` branch.

3. **`download_jd_config`** — JDownloader connection + device config, replacing env vars.
   - Columns: `id INTEGER PRIMARY KEY CHECK (id = 1)` (singleton row pattern, same idea as a settings table), `myjd_email TEXT`, `myjd_password_encrypted BLOB`, `device_name TEXT`, `exe_path_override TEXT` (nullable — fallback to reading Autoreas Settings `downloader.dir` if null), `last_seen_status TEXT`, `last_seen_at_ms INTEGER`, `default_dest_dir TEXT`.
   - **Security note**: `myjd_password_encrypted` — at minimum DPAPI (Windows Data Protection API) via `golang.org/x/sys/windows` should encrypt-at-rest scoped to the current Windows user, since `bridge.db` is not itself encrypted and lives in a user-writable `%APPDATA%` path. Storing plaintext in SQLite is a strict regression versus even the current `.env`-gitignored-file approach (which at least isn't a queryable DB).
   - "Can we store more about JD" — yes: device name, last-seen online/offline status + timestamp (feeds the management UI's live status), default destination directory (separate from per-anime `carpeta`, useful as a fallback), and optionally a cached device list snapshot for diagnostics.

4. **`download_schedule_config`** — scheduled task time/cadence.
   - Columns: `id INTEGER PRIMARY KEY CHECK (id = 1)`, `mode TEXT NOT NULL` (`"windows_task"` or `"in_process"` — see Approaches Compared below), `cron_or_time TEXT` (either a daily HH:MM or a cron-like expression depending on chosen mode), `enabled INTEGER NOT NULL DEFAULT 1`, `last_run_at_ms INTEGER`, `last_run_status TEXT`, `next_run_at_ms INTEGER`.
   - This table is the single source of truth regardless of which scheduling mechanism (Windows Task Scheduler vs in-process timer) is chosen in design — the UI reads/writes this table either way; only the *executor* of the schedule differs.

5. **`download_runs`** (telemetry/log table, additive to — not a replacement for — the shared observability `LogEntry` stream).
   - Columns: `run_id TEXT PRIMARY KEY`, `started_at_ms INTEGER NOT NULL`, `finished_at_ms INTEGER`, `trigger TEXT` (`"scheduled"`/`"manual"`), `animes_checked INTEGER`, `episodes_found INTEGER`, `episodes_downloaded INTEGER`, `episodes_failed INTEGER`, `jd_available INTEGER`, `status TEXT` (`"ok"`/`"partial"`/`"error"`/`"jd_offline"`/`"no_animes_today"`), `error_summary TEXT`.
   - **Tie to SDD-20 observability**: per-run summary rows are a *complement* to, not a substitute for, structured `logger.Logger.Logf(domain="download", ..., Fields{CorrelationID: runID, EntityID: animeID, EventType: "download.episode_downloaded", DurationMs: ...})` calls during the run. The existing `LogEntry` shape (already extended with `CorrelationID/EntityID/EventType/DurationMs/Metadata` per SDD-20) is sufficient for live/session observability (`MemLogger` ring buffer + `ObservabilityPanel`); `download_runs` exists because the ring buffer is bounded (500 entries) and not persisted across restarts, so historical "did last night's scheduled run succeed" queries need a durable table. Both should share the same `run_id` as `CorrelationID` so a UI can cross-reference a `download_runs` row to its detailed log entries (while the session ring buffer holds them) or — if the user wants durable detailed history — to a new `download_run_events` child table (optional, can be deferred).

6. **Legacy backfill for `pagina`/`carpeta`** — confirmed via `internal/anime/domain/anime_raw.go`: both fields are `LegacyStringField` with full tri-state semantics (`IsAbsent()/IsNull()/IsPresent()`), exactly like every other optional legacy field. There is **no schema migration needed on the `anime_snapshots` table** — the snapshot JSON already carries whatever the legacy app wrote, including absence. The actual "backfill" problem is **operational, not structural**: some real anime records will have `Pagina` absent or `Carpeta` absent/empty, and the download feature must explicitly handle and surface "anime X has no download page configured" / "anime X has no folder configured" as a *visible, actionable state* in the management UI (not a silent skip like the PoC's `fmt.Printf("⏭ Sin página")`) — this is a UX/observability requirement, not a SQLite migration.

## UI Surface Analysis

Mapped against `AGENTS.md` frontend constraints (dumb `.tsx`, strict hook anatomy, colocation, readonly props, JSDoc helpers, 500-line cap) and the existing `frontend/src/features/{network,dashboard}` precedents.

A new `frontend/src/features/download` (scaffolded via `bun --cwd="frontend" run generate:feature download <ComponentName>`, per AGENTS.md rule 10) must expose, at minimum:

1. **Hoster priority editor** — analogous to `NetworkFilterBar`'s controlled-filter pattern but as a reorderable list (drag-or-buttons) bound to `download_hoster_priority`; persists via a Wails-bound `SetHosterPriority(site, []string)` call.
2. **JDownloader config panel** — device name, email (password write-only, never round-tripped back to the UI in cleartext), exe path override, plus a **live status indicator** (online/offline, last seen) sourced from a Wails-bound `GetJDStatus()` poll or push via the event bus → `observability.log`-style emit.
3. **Schedule config panel** — mode selector (if both Windows Task and in-process are kept as options) + time/cadence input + enable toggle + "next run" / "last run status" display, mirroring `download_schedule_config`.
4. **Run history / logs panel** — reuse the `NetworkPanel` master/detail pattern (table of `download_runs` rows + detail view per run) OR extend `ObservabilityPanel`'s live feed filtered to `domain=download`. Given `NetworkPanel` already solves "filter bar + dense table + detail inspector + status bar counts," it is the stronger structural precedent for run history specifically; `ObservabilityPanel` remains correct for the *live, in-session* log feed.
5. **Manual trigger button** — a single Wails-bound `TriggerDownloadCheck()` call (same shape as the existing `TriggerReconcile()` on `App`), with a loading/last-result state in the UI.
6. **Per-anime page/folder gap indicator** — surfaces animes missing `pagina`/`carpeta` so the user can fix them in the legacy app, addressing the backfill UX gap noted above. Could live inside the existing `AnimePanel` (`frontend/src/features/anime/ui/AnimePanel`) as an additional filter/badge rather than a new component, since it's anime-data-quality information, not download-run information.

All business logic (Wails calls, polling, derived "is JD online" booleans, etc.) belongs in colocated `use-*.ts` hooks per the mandatory hook anatomy; `.tsx` files render only.

## Open Questions & Decisions for the Proposal/Design Phases

1. **Bounded context name and granularity** — single `internal/download` context owning scrape+acquire+filesystem+schedule, OR split into `internal/scrape` (site adapters, reusable for future non-download scraping needs) + `internal/acquisition` (JD integration + filesystem + trigger decision)? Tradeoff: a single context is simpler to wire in `app.go` now; a split pays off only if scraping is ever reused outside downloading (no evidence of that yet). Lean toward single context with clear internal package boundaries (`internal/download/sites`, `internal/download/jdownloader`, `internal/download/filesystem`) rather than separate top-level bounded contexts — revisit if reuse materializes.
2. **Scheduling mechanism** — Windows Scheduled Task (external, OS-level) vs in-process scheduler (Go `time.Timer`/cron-lib inside the already-running Wails tray app). See Approaches Compared below; this is probably the single highest-leverage decision in the whole feature.
3. **Multi-site extensibility timing** — build the `source`-style registry now (even with only jkanime registered) so the seam exists, or defer until a second site is actually requested? Recommendation: build the registry now (low marginal cost given dlexa's pattern is copy-adaptable) because the alternative (PoC's `strings.Contains` branch) actively blocks any future site without a rewrite.
4. **Películas/OVAs (Tipo 1/2) handling** — the PoC's data model carries `Tipo` but never branches on it; episode-counting/page-URL conventions for movies/OVAs on jkanime may differ from series (single "episode," different URL shape). Needs explicit scraper-adapter logic or an explicit "not yet supported, surfaced as a skip reason in the UI" decision — must not silently mis-trigger.
5. **Idempotency/concurrency with append-only writer + sync engine** — the download feature only *reads* `anime_snapshots` (via the proper query service) and writes its own new tables; it does not (in the PoC) write back to `animes.dat` or bump `NroCapVisto`. The user explicitly flagged "persisting NroCapVisto after successful download" as an omission. Decision needed: should the official feature actually write `NroCapVisto` back through the existing `AnimeWriteService.PatchAnime` (reusing the Append-Only Writer + Self-Echo-safe path that already exists), or is that intentionally out of scope (legacy desktop app remains the only writer of viewing progress)? If in-scope, this reuses an existing, hardened write path — no new concurrency risk beyond what `PatchAnime` already handles. If out-of-scope, it must be explicitly documented as a known gap, because the user explicitly flagged it.
6. **Captcha fallback strategy** — the PoC's batch-by-hoster loop falls through to the next hoster on enqueue failure, but does not specifically detect *captcha* vs *generic failure* vs *hoster temporarily down*. Does the official feature need actual captcha detection (e.g. via response-content heuristics) or is "try next hoster after N failed attempts/timeout" sufficient? Current PoC's 30-minute filesystem-polling timeout already provides an implicit fallback signal but conflates "captcha blocked" with "slow download" with "hoster dead" — telemetry (the `download_runs.error_summary` / structured log `EventType`) should at least distinguish these for the user even if no programmatic captcha-solving is attempted.
7. **JD credential storage mechanism** — DPAPI-encrypted column in `bridge.db` (proposed above) vs Windows Credential Manager (`wincred`) vs continuing with a gitignored `.env`-style file but now bridge-managed instead of user-edited. DPAPI-in-SQLite keeps everything in the existing single-database operational model (one file to back up/migrate); Credential Manager is more idiomatically "secure" on Windows but introduces a second persistence mechanism the bridge doesn't otherwise have. Recommend DPAPI-in-SQLite for consistency, flag Credential Manager as the more-secure alternative for the architect to weigh.
8. **HTML parsing robustness** — keep regex-based extraction (fast to ship, validated working today) or invest in `golang.org/x/net/html`-based DOM parsing now (more resilient to jkanime template drift, but added dependency + rewrite cost) before the official feature ships? The PoC's own README already names this as a known weakness. Recommend at minimum isolating extraction behind the `source`/`engine.Resolver`-style adapter interface so the *implementation* (regex today, DOM parser later) can change without touching orchestration — defer the rewrite itself unless proposal phase has time budget.
9. **JD-offline / no-LAN behavior** — PoC already has graceful degradation (`printManualDownload` + notify). Does the official feature need this preserved as a first-class "manual mode" surfaced in the UI (e.g. a `download_runs` row with `status="jd_offline"` and a list of manual links persisted somewhere the user can retrieve from the UI), or is silent retry-next-scheduled-run acceptable? User did not explicitly ask for manual-mode UI; recommend persisting the manual-links list against the `download_runs` row (as JSON) so the existing run-history UI can surface it for free, rather than inventing a separate manual-download UI.

## Risks & Boundary Truths

- **Concurrency with append-only writer & sync engine**: SAFE as long as the download feature only reads through `AnimeQueryService` and (if NroCapVisto-write is in scope, see open question 5) only writes through the existing `AnimeWriteService.PatchAnime` — both paths already solve Windows file-locking, Self-Echo, and single-writer-channel concerns. Any temptation to open `animes.dat` directly from the new context (as the PoC's fallback `-data` flag flow does) must be rejected for production; only the legacy CLI/dev fallback, if kept at all, may do that, and never in a shipped, scheduled, unattended run.
- **JD offline / no LAN**: `Connect()` succeeding while JD is actually offline is a real, reproducible API quirk (confirmed in PoC code, not hearsay) — any new health-check/doctor-style check for "is JD ready" must call `ListDevices()`, never trust `Connect()` alone.
- **Captcha / hoster failure ambiguity**: current batch-by-hoster fallback is a blunt instrument (timeout-based); without explicit telemetry distinguishing failure causes, repeated unattended scheduled runs could silently fail the same way every night with no actionable signal to the user beyond "0 downloaded."
- **Security of MyJD credentials**: current PoC approach (plaintext env vars / `.env` file) is acceptable for a developer-run PoC, unacceptable for a shipped, scheduled, unattended feature that other people may end up running. Must be resolved in design (see Open Question 7) before this ships — this is a hard blocker, not a nice-to-have.
- **Windows Scheduled Task vs in-process**: the bridge is `HideWindowOnClose: true` (`main.go`) — i.e. closing the window does NOT exit the process; the Wails app (and therefore an in-process scheduler) keeps running in the tray as long as the OS process is alive. This materially weakens the case for an external Windows Scheduled Task purely for "the app might not be running" reasons — the tray app is *designed* to stay running. The remaining argument for a Scheduled Task is surviving a full machine reboot before the user manually relaunches the bridge, and running even if the user has fully quit (not just hidden) the app. See Approaches Compared.
- **Multi-site extensibility**: every hardcoded `jkanime.net`/`jkanime.bz` string-contains check in the PoC is a single point of total failure for any future site; must be replaced by a registry-driven dispatch before any second site is added, not after.
- **Películas/OVAs**: currently completely unhandled in PoC trigger/scrape logic (the `Tipo` field is read but never branches on it) — silently broken today for any movie/OVA-type "anime," not just "future scope."
- **Legacy data gaps (`pagina`/`carpeta` absent)**: already structurally tolerated by `LegacyAnimeRaw`'s tri-state fields; the real risk is *silent* skipping in the UI rather than any parser crash.

## Approaches Compared

### A. Scheduling: Windows Scheduled Task vs in-process scheduler

| Approach | Pros | Cons | Effort |
|---|---|---|---|
| **Windows Scheduled Task** (registers a separate invocation, e.g. `autoreas-bridge.exe --download-check` or a slim companion binary, via `schtasks`/Task Scheduler COM API) | Survives full app exit (not just hidden window) and machine reboot without requiring the user to have the tray app open at all; OS-native retry/logging; decoupled from Wails process lifecycle entirely | Requires either a second invocation mode for the same binary or a separate process; needs install/uninstall logic (privilege considerations, `schtasks /create` is doable without admin for per-user tasks but still adds installer complexity); duplicates "is this even still the right binary path" maintenance burden if the app is reinstalled/moved; harder to test/observe (runs outside any debugger attached to the live app) | High |
| **In-process scheduler** (Go ticker/cron-lib running inside the already-resident Wails tray process, gated by `download_schedule_config`) | Trivial to test (it's just a goroutine with a timer, same composition-root pattern as every other `app.go`-wired service); shares the live event bus/logger/observability stack for free; no separate install/permission story; consistent with `HideWindowOnClose: true` design intent (the app is *meant* to stay resident) | Does NOT run if the user has fully quit the app (real `quitApp`/`requestQuit` path) or the machine just rebooted and the app hasn't auto-started yet; depends on bridge's own auto-start-on-login configuration (if any) being reliable | Low–Medium |

**Recommendation**: in-process scheduler as the primary mechanism, because the app's own `HideWindowOnClose: true` design already assumes long-lived residency, and it reuses 100% of the existing composition-root/event-bus/observability investment with no new install-time complexity. Revisit Windows Scheduled Task only if the bridge does NOT already have (or plan) auto-start-on-login — if it lacks that, a Scheduled Task may be the more reliable way to guarantee the check runs even after a reboot the user doesn't immediately follow by reopening the app. This is exactly the kind of cross-cutting platform decision the design phase should confirm against the bridge's actual auto-start story (`internal/system` per `docs/architecture.md` §1.4 "Arrancar la app, registrar Auto-start en el OS" — if that's implemented, in-process scheduling is strictly sufficient and simpler).

### B. Bounded context shape: single `download` context vs split `scrape`/`acquire`

| Approach | Pros | Cons | Effort |
|---|---|---|---|
| **Single `internal/download` context** with internal sub-packages (`sites/`, `jdownloader/`, `filesystem/`, `schedule/`) | One service to wire in `app.go`; one set of SQLite tables under one logical owner; matches the `device` context's scale (single `Service` + `Store`) which is the established precedent in this codebase | If scraping logic is ever needed by an unrelated feature, it's nested inside `download` and harder to extract later | Low |
| **Split `internal/scrape` (generic site-scraping infra, reusable) + `internal/acquisition` (JD + filesystem + decision + schedule)** | Cleaner reuse boundary if scraping is ever needed elsewhere; mirrors dlexa's `source`/`fetch`/`parse` separation more literally | Two contexts to wire, two sets of inter-context calls for a feature that currently has exactly one consumer of scraping (downloading); premature generalization given no second scraping use case exists today | Medium |

**Recommendation**: single `internal/download` context with strong internal package boundaries (mirroring dlexa's `source`/`fetch`/`parse` separation *inside* `internal/download`, not as separate top-level bounded contexts). Promote to a split only if/when a second, genuinely independent consumer of site-scraping emerges — YAGNI applies cleanly here since the codebase's own precedent (`device`) shows single-context-per-capability is the established granularity.
