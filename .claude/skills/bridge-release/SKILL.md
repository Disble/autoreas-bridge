# Releasing autoreas-bridge

The version is declared in **one** place: `info.productVersion` in `wails.json`.
Everything else is generated from it.

Every release also updates `CHANGELOG.md`. A bump without a changelog entry is an
incomplete release.

## Hard Rules

- **Every release updates `CHANGELOG.md`.** Promote `## [Unreleased]` to the new
  `## [X.Y.Z] — YYYY-MM-DD` heading and leave a fresh empty `## [Unreleased]`
  above it. Commit it with `wails.json` and the regenerated installer, in the
  same commit — the version, the installer, and the notes ship together or the
  release is a lie.
- **Write the changelog for the user, not the git log.** Entries say what changed
  for someone using the app, in the app's own vocabulary. `feat(download):
  partition solo download rail` is a commit subject; "Downloads now separates
  anime that are ready to download from those that are blocked" is a changelog
  entry. Never paste commit subjects.
- Group under Keep a Changelog headings — `Added`, `Changed`, `Deprecated`,
  `Removed`, `Fixed`, `Security` — plus `Internal` for changes with no
  user-visible effect. Omit headings with nothing under them.
- **Call out wire changes explicitly.** REST/WS contracts have mobile consumers;
  a wire-affecting release says so under its heading, and a breaking one is a
  major bump announced in `docs/openapi.yaml`.
- Never hand-edit `build/windows/installer/wails_tools.nsh`. It is generated by
  `wails build -nsis`; edits are silently overwritten on the next build.
- Never commit `build/bin/**`. It is gitignored — artifacts ship, they do not
  get versioned.
- Commit `wails.json` and the regenerated `wails_tools.nsh` in the **same**
  commit. A version in `wails.json` without its regenerated installer is a lie.
- A missing `info.productVersion` means the build silently falls back to Wails'
  hardcoded `1.0.0`. Absence is never a declared version — treat it as unset.
- Never `--no-verify`. The gate takes ~90s–300s; give `git commit` a timeout
  of at least 300000 ms.
- Known open bug: the built `.exe` has blank Windows file properties
  (ProductName/ProductVersion/FileVersion all empty). The **installer** version
  is correct. Do not report this as a regression caused by a bump.

## Decision Gates

| Change shipped | Bump |
|---|---|
| Bug fix, no contract or UX change | patch — `1.0.0` → `1.0.1` |
| New feature, backward compatible | minor — `1.0.1` → `1.1.0` |
| Breaking wire/DB/config change | major — `1.1.0` → `2.0.0` |

Wire contracts have mobile consumers: a breaking REST/WS change is major and
must also be announced in `docs/openapi.yaml`.

## Execution Steps

1. Read the current version: `rg productVersion wails.json`. If absent, the
   effective version is `1.0.0`.
2. Review what actually shipped since the last release bump
   (`git log --oneline <last-release-sha>..HEAD`) and decide the bump from the
   Decision Gates below.
3. Set the new `info.productVersion` in `wails.json`.
4. Update `CHANGELOG.md`: promote `## [Unreleased]` to `## [X.Y.Z] — YYYY-MM-DD`,
   add a fresh empty `## [Unreleased]` above it, and write the entries in user
   language under the Keep a Changelog headings.
5. Build: `wails build -platform windows/amd64 -nsis -clean`.
6. Verify the regenerated define matches:
   `rg 'INFO_PRODUCTVERSION "' build/windows/installer/wails_tools.nsh`.
7. Confirm both artifacts exist in `build/bin/`: `autoreas-bridge.exe` and
   `autoreas-bridge-amd64-installer.exe`.
8. Smoke-test the built binary for anything tests cannot reach (window/tray
   behavior, single-instance, installer flow). Report it as unverified if you
   cannot run it — never imply you did.
9. Append the release rationale to `docs/learning-log.md` with
   `node scripts/log-lesson.mjs "..."` — never by hand.
10. Commit `wails.json`, `CHANGELOG.md`, `wails_tools.nsh`, and the log as
    `chore(release): bump to X.Y.Z and regenerate installer`.

## Output Contract

Report: the old and new version, the regenerated `INFO_PRODUCTVERSION`, the
changelog section written, both artifact paths with sizes, the gate result, and
explicitly which runtime checks were smoke-tested versus left unverified.
